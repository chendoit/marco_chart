### 1. 日/小時層：排程、規則門檻與反證邏輯

* **排程公布時間與調度器對齊（反對／補充）**
  * **整點調度器 vs 分鐘級發布**：`dispatcher.py` 是每小時**整點**喚醒，草案寫 21:45、02:45、02:15 實務上只會在 **22:00、03:00** 被執行。建議表格直接標註「實際觸發整點（21:00、22:00、03:00、05:00、06:00、09:00）」，並用程式根據 `America/New_York` 動態換算台北時間，避免 EST/EDT 夏令時間切換寫死出錯。
  * **SOFR 落後性問題**：SOFR 是 T+1 08:00 ET（台北 21:00）才公布**前一個交易日**的數據。若週三盤中發生擠壓，SOFR 要週四 21:00 才看得到。因此真正的**當日盤中即時指標**只有 ON RRP（02:15）與兩場 SRF（21:45、02:45），這點在狀態機權重上必須區分「T+0 即時」與「T+1 落後」。
  * **資料源挑選**：D3/D4/E3（H.4.1）建議直接打聯準會官網週四 16:30 ET 發布的 H.4.1 XML/CSV，不要等 FRED（FRED 常延遲到週五早上甚至下午才更新 `WRESBAL`）。
* **規則門檻修正（反對／調整）**
  * **R1（SOFR−IORB）**：2026 年底準備金已降至 2.89 兆，摩擦性利差轉正是常態（10/23–11/5 連 10 日為正）。設 ≥ +3bp 會天天亮燈。**具體做法**：改為「利差 ≥ +5bp（1 級）、≥ +8bp（2 級），或 5 日移動平均 ≥ +5bp 且較 20 日均線跳升 > 3bp」。
  * **R2（SOFR P99 − SRF）**：10/27 P99 4.04% 高過 SRF（4.00%）4bp 但無事發生，因少數非銀機構無 SRF 資格。門檻應改為 **> +5bp（2 級）、> +10bp（3 級）**。
  * **R4（SRF 用量）**：不能把「壓力極大」跟「Fed 救市紓解」混為同一個警報！平日（非季底）SRF > 20 億美元就是流動性阻塞警訊（1 級），> 100 億是嚴重擠壓（2 級）。至於「> 150 億止跌」應拆成另一條「政策干預觀察」，而非直接當紓解。

  * **R10（黃金殘差 B3）**：`WN.md` 已證實兩因子日變動回歸 $R^2$ 僅 0.15–0.18，殘差幾乎等於黃金自身跌幅，毫無獨立資訊。**建議廢除 R10**，併入 R9 的黃金 z-score 即可。

### 2. 綜合狀態與日曆效應的做法

* **反對固定「最高等級」與「日曆直接降一級」**
  * 季底/月底若完全降級，會漏掉「季底引爆真危機」（如 2019 年 9 月中稅日+結算日）；非日曆日若單靠 R5（準備金 < 2.85 兆，週頻常駐）直接取 max，系統會**連續幾個月卡在橘燈**，喪失警報功能。
* **替代方案：拆分為「慢速背景水位（Regime）」與「快速衝擊分數（Shock）」**
  1. **背景水位（週頻 D3/D4/D2/F3）**：只決定「脆弱度（Fragile / Normal）」，**不直接發警報**。例如準備金 < 2.9 兆且 CFTC 槓桿基金淨空單處於歷史 > 80% 分位 → 背景設為 `Fragile`。
  2. **日內/日度衝擊（C 組、E1、A4）**：決定燈號。在 `Fragile` 下門檻維持原值；`Normal` 下門檻加嚴 1.5 倍。
  3. **日曆效應改為「動態基線調整」而非降級**：在月底、季底、大額結算日（> 500 億），把 R1（SOFR−IORB）門檻**加寬 +3bp**、R4（SRF）門檻**加寬 +100 億**。若超過加寬後門檻，照樣升紅燈！再加一條：**日曆日 T+2 若利差未回落超過 50%，強制升為 2 級警戒**（流動性卡死未消退）。

### 3. 如何避免變成「天天喊狼來了」或「確認偏誤機器」？

* **補充具體機制**
  1. **強制輸出「競爭假說計分板（Competing Hypotheses）」**：警報觸發時，腳本與下游 Agent 不可只寫「美元水管擠壓」，必須同時對三個假說打分並列印在 Telegram：
     * **H_Liq（美元融資擠壓）**：需 SOFR−IORB 衝高 + `SOFR−TGCR` 擴大 + **DXY 上漲** + 股金債齊跌。
     * **H_Macro（鷹派／成長衝擊）**：如 11/5 大跌，利差僅 +2bp，或是 10/28 FedWatch 升息機率跳升 69pp、科技巨頭財報暴雷（10/30 INTC −28.6%、SOX −7.2%）。
     * **H_Delev（純部位／Gamma 追繳砍倉）**：融資端平靜或美元下跌，但 SPX 跌破 Gamma Flip 且高 Beta 與黃金在特定時窗（如 15:45）同步遭拋售。
  2. **T+1 / T+3 自動驗屍（Auto-Postmortem）**：`alerts.jsonl` 觸發後，腳本在 T+1 與 T+3 自動回填後續表現（SPX、GLD、SOFR 變化），每週五 21:00 心跳摘要附上「本週訊號勝率與假陽性檢討」。

### 4. 分鐘層：方案 A vs B vs C

* **反對方案 A 與 B，推薦「方案 C：輕量 API 5m 輪詢 + TV Desktop 按需快照」**
  * **方案 A 的致命傷**：TradingView 的 `deploy_pine.mjs` 雖然能改 Pine 參數，但**伺服器端已建立的 Alert 實例通常綁定建立當下的腳本快照與參數**，除非透過 UI 自動化刪除並重建 Alert，否則每日更新的 `regime` 與 `gamma flip` 根本不會同步進既有 Alert！此外，Webhook 需付費方案，還要自架公網中繼（ngrok/Cloudflare Tunnel）轉 Telegram，增加無謂的維運脆弱點。
  * **方案 B 的缺點**：TV Desktop 24 小時常駐開著容易記憶體洩漏或斷線。
  * **方案 C（具體做法）**：
    1. 既然只關心**特定時窗**（開盤 09:30–10:00、倫敦定盤 05:30/10:00 ET、尾盤 15:30–16:00 ET）或**日層已亮黃燈以上**，根本不需要 24 小時跑分鐘監控。
    2. 在 `dispatcher.py` 或獨立輕量腳本中，**僅當日層 `state >= 黃燈` 或處於上述美股關鍵時窗**，直接用 Python 抓取 Yahoo Finance 5m API（`QQQ`, `GLD`, `ZN=F`, `DX-Y.NYB`, `BTC-USD`, `^GSPC` 支援免費 5m 報價，延遲極低且不需開桌面程式）。
    3. 腳本算出 30 分鐘滾動 z-score 確認跨資產同跌或 SPX 跌破 `gex_spx_gamma_flip` 時，**才按需喚醒** `tv_client.py` 抓 `OANDA:XAUUSD` 5m 精確驗證並截圖，直接由本機 `liq_notify.py` 推播 Telegram。零 Webhook 成本、零 Alert 同步問題、平時零資源消耗。
